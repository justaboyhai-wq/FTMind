# FTMind 政策知识库自循环说明页设计

## 目标

为产品人员制作一份可直接在浏览器打开的单文件 HTML，说明 FTMind 政策知识库的核心业务逻辑。页面以“知识如何持续更新、如何被验证、如何通过用户反馈继续生长”为主线，不罗列全部系统功能，也不写成部署手册或接口参考。

## 受众与表达原则

- 主要受众：产品经理、产品负责人及参与政策知识产品规划的业务人员。
- 先讲业务闭环，再解释必要的技术机制。
- 严格区分当前代码已经实现的能力和建议中的演进方向。
- 不展示服务器密码、数据库口令、Token、密钥或内部请求头。
- 使用当前产品名 `FTMind`；代码、协议或历史文件中的 `FTMind` 标识不作为页面品牌展示。

## 代码事实依据

页面只陈述以下已经从项目代码与文档核验的事实：

1. 宝安政策采集器每次从入口 HTML 重新发现 `zcfg.js`，并采集详情 JSON、政策原文 HTML、附件、官网标签与显式关系，输出不可变 Raw Package。
2. 采集器支持全量、增量、失败重试和定时任务；调度采用 Asia/Shanghai 时区，并跳过重叠执行。
3. RSS 网关只读展示 Raw Package 的最新快照；`/feed.xml` 提供内容，`/healthz` 校验所有最新包能否成功装配。后续增量采集会被下一次 RSS 同步感知。
4. FTMind 的 RSS 连接器支持全量与增量同步，以 Feed 信号和正文指纹判断条目是否变化，并保留官方标签。
5. 政策 Wiki Schema 将字段划分为 `official`、`computed` 和 `derived_ai` 三个命名空间。官网字段不能由模型补写或覆盖；动态申报状态需要记录计算时间、依据和证据；AI 派生字段需要模型、提示词版本、置信度、证据和审核状态。
6. 回答反馈模型冻结问题、答案、引用、模型、智能体、渠道等必要快照，具有 `pending`、`reviewing`、`needs_info`、`fixing`、`resolved`、`dismissed` 状态和事件时间线。管理员标记已解决时必须填写根因、处理方式和公开回复。
7. 收藏能力当前是用户级、空间隔离的资源收藏，服务层明确不触发跨聚合副作用。因此页面不得声称收藏会自动写回知识库，只能将其描述为高价值候选信号，后续由管理员审核后进入优化流程。
8. 共享空间支持共享知识库和智能体；共享不改变原始归属。空间角色为管理员、编辑者、只读，知识库共享还具有只读/可写权限，最终能力受成员角色和共享权限共同约束。

## 页面信息架构

### 1. 首屏：产品定位

标题为“FTMind 政策知识库：从官方资料到持续生长的知识循环”。副标题说明它不是静态文档仓库，而是一套围绕政策证据、持续同步、受控解析和人工审核构建的知识更新系统。

首屏提供四个核心能力摘要：官方资料留存、RSS 增量更新、证据化 Wiki、反馈审核闭环。

### 2. 演示环境

以简洁表格列出：

| 项目 | 当前配置 |
| --- | --- |
| 云端主站 | `http://115.191.64.43:18310` |
| 登录入口 | `http://115.191.64.43:18310/login` |
| 宝安政策 RSS 端口 | `18320` |
| RSS Feed | `http://115.191.64.43:18320/feed.xml` |
| RSS 健康检查 | `http://115.191.64.43:18320/healthz` |

同时注明：仓库默认配置将 RSS 绑定在 `127.0.0.1:18320`，产品环境可通过现有 Nginx 反向代理提供访问；页面展示的直连地址仅代表当前部署约定，实际可达性取决于服务器绑定和安全组。

### 3. 官方政策资料循环

用横向流程表达：

`宝安官网入口 → zcfg.js 发现 → 原文/JSON/附件/标签下载 → Raw Package → 只读 RSS → FTMind 增量同步 → 解析与索引`

强调 Raw Package 保存原始证据与校验信息，RSS 负责稳定发布最新可用快照，FTMind 连接器通过指纹进行增量判断。采集和知识库同步是两个解耦的周期。

### 4. Wiki 规则与可信边界

以三层卡片解释：

- 官方事实 `official`：官网标题、文号、机构、日期、服务对象、主题、载体、附件和关联内容等，原样保留来源与证据。
- 规则计算 `computed`：如“当前是否可申报”，必须记录算法版本、计算时间、输入证据与冲突信息。
- 模型分析 `derived_ai`：如适用行业、办理条件、材料、流程和风险提示，只能形成新分析维度，不能伪装成官网标签。

再展示 Wiki 操作日志和质量问题如何支持更新、失效、替代、回滚与人工审核，而不是直接覆盖历史事实。

### 5. 问答与用户信号

问答链路强调“先检索证据，再形成回答”，并保存政策原文、附件、Wiki 页面和来源 URL 的引用关系。

用户侧展示两个信号入口：

- 收藏：记录用户认为值得复用的资源或内容，作为产品和知识运营的价值信号；当前不会自动改写知识库。
- 错误反馈：关联一次真实问答，冻结必要快照，进入可跟踪工单。

### 6. 管理员审核与修复闭环

使用状态流程：

`待处理 → 审核中 → 待补充/修复中 → 复测 → 已解决或驳回`

根因可落到原始资料、解析/分块/索引、检索/重排、Wiki、智能体提示词、模型、政策更新或用户条件不足。修复不得由反馈直接触发政策内容修改，必须由管理员确认、执行、复测和发布公开结论。

收藏与反馈都可以成为知识优化候选；只有审核通过的内容才能重新采集、重解析、调整 Wiki 或作为回归样例沉淀。

### 7. 共享空间与权限

解释四个关系：资源始终归属于原空间；共享空间只保存协作关系；成员角色决定人在共享空间中的上限；知识库共享权限决定该资源允许的能力。最终权限取成员角色与共享权限的交集。

说明智能体共享为只读使用；知识库可按共享空间分别设置只读或可写，不同空间互不影响。

### 8. 双循环收束

页面结尾用两个相互连接的循环总结产品方向：

- 内容循环：`官网更新 → 定时采集 → RSS 增量同步 → Wiki/索引更新 → 政策问答`。
- 质量循环：`问答使用 → 收藏/错误反馈 → 管理员审核 → 修复复测 → 重新进入知识体系`。

核心结论：系统的“生长”不是让模型自由改写政策，而是让官方证据、规则计算、模型分析和人工治理在清晰边界内持续协作。

## 视觉与交互设计

- 单文件 HTML，CSS 与少量 JavaScript 全部内联，不依赖外部字体、图片或 CDN。
- 桌面优先，同时在 900px 以下切换为单栏布局。
- 使用深蓝与浅蓝作为主色，辅以绿色表示已验证、橙色表示待审核。
- 左侧为章节导航，中间为正文，右侧为本页目录；窄屏隐藏右侧目录并将左侧导航转换为顶部区域。
- 循环关系使用纯 HTML/CSS 卡片和箭头，不使用 Canvas 或外部图形库。
- 提供页面内锚点、当前章节高亮和返回顶部入口。

## 内容边界

页面不包含：

- 全部模型配置、向量数据库和基础设施清单；
- API 详细参数或数据库表结构；
- 用户名、密码、Token、密钥；
- 对尚未实现的自动知识回写、自动发布或无人审核修改的承诺；
- 政策采集器以外的通用数据源功能展开。

## 验收标准

1. 产品人员在 5 分钟内能理解政策资料循环和质量反馈循环。
2. 页面准确展示当前云端入口和 RSS 端口，并注明网络可达性边界。
3. 页面能清楚区分官方事实、规则计算和模型分析。
4. 页面能解释收藏、错误反馈、管理员审核和知识再注入之间的真实关系。
5. 页面能说明共享空间、成员角色与资源共享权限如何共同生效。
6. 文件可离线打开，无外部资源依赖；1280px 和手机宽度均可阅读。
7. 不含敏感凭据，不将规划能力误写为已实现能力。
